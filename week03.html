Data Structures, Entities, Attributes & Keys

How founders decompose messy "One Big Table" spreadsheets and nested JSON event logs into clean, relational schemas ready for SQL, BI, and AI.

Structure Precedes AI & Analytics

  • Core Innovation Questions: Who are our customers? What do they buy? When do they churn?
  • Why Flat Sheets Fail: Cramming Customer, Product, and Order facts into one sheet breaks analytics and AI pipelines.
  • Redundancy Overhead: Repeating $k$ customer attributes across $m$ orders creates duplicate storage ($R_{\text{dup}} = (m - 1) \cdot k$).
  • Update Anomalies: Changing one customer's email or product price requires editing multiple rows, causing data conflicts.
$$\text{Row Grain} = \text{Exact real-world event or object represented by } 1 \text{ row}$$
  • Rows = individual records
  • Columns = single atomic facts
  • Tables = single entity meaning

Primary Keys ($PK$) & Foreign Keys ($FK$)

  • Primary Key ($PK$) Purpose: Uniquely identifies every single row in a table.
  • What to Avoid: Never use personal names (duplicates exist) or phone numbers/emails (users change them).
  • Foreign Key ($FK$) Link: When an Order stores CustomerID, it connects the child row to its parent record for SQL joins and totals ($\text{Total} = \\sum p_i q_i \cdot (1 + r_{\text{tax}})$).
$$\forall r_i, r_j \in T \text{ with } i \neq j: \quad PK(r_i) \neq PK(r_j) \;\;\land\;\; PK(r_i) \neq \varnothing$$
  • Rule 1: Strictly Unique across all rows
  • Rule 2: Never NULL or empty
  • Rule 3: Never Reused after deletion

Milestone 1 Prep: Nested JSON Product Event Logs

Modern startups capture mobile and web telemetry as nested JSON event logs at the API gateway, then flatten them into relational CSV / PostgreSQL tables using shared keys (user_id, order_id, event_id).

Flattened Relational Mapping (Milestone 1 Blueprint)

Each nested object in the JSON log maps cleanly into its own relational table with an explicit row grain:

1. users table (Grain: 1 row per registered user)
user_id (PK), first_name, last_name, email, signup_date

2. orders table (Grain: 1 row per order header)
order_id (PK), user_id (FK), order_ts, status_code

3. product_events table (Grain: 1 row per app event)
event_id (PK), user_id (FK), order_id (FK), event_name, event_ts
